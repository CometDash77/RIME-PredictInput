## 2. 正在追的根因（假设按优先级排序，均未实证）

关键代码事实（已核实，直接可用）：

- `WeaselIPC\WeaselClientImpl.cpp:189-201` `ClientImpl::UpdatePredictContext`：`_Active()` 门控 → `BuildBody(status, escape_string<wchar_t>(text), revision)` → `channel << body.c_str()`（置 has_body=true）→ `return _SendMessage(WEASEL_IPC_PREDICT_CONTEXT, 0, session_id) != 0`。
- `WeaselIPC\WeaselClientImpl.cpp:211-220` `_SendMessage` = `channel.Transact(PipeMessage{Msg,wParam,lParam})`，DWORD 异常吞掉返 0。
- `WeaselIPC\PipeChannel.cpp:101-114` `_Receive`：第一次 ReadFile 读固定头（服务端 sizeof(PipeMessage)=12B），ERROR_MORE_DATA 时第二次 ReadFile 把余下数据读进 `buffer.get()` **从 buffer 偏移 0 开始**；结束时 has_body=false。
- `WeaselIPC\PipeChannel.h:106-108`：`SendBuffer() = buffer.get()+_MsgSize`；`ReceiveBuffer() = buffer.get()+_ResSize`。
- 服务端通道类型 `WeaselIPCServer\WeaselServerImpl.cpp:9` `class PipeServer : public PipeChannel<DWORD, PipeMessage>` → 服务端 `_ResSize = sizeof(PipeMessage) = 12`，`_MsgSize = sizeof(DWORD) = 4`。
- `WeaselIPCServer\WeaselServerImpl.cpp:366-377` `OnPredictContext`：`m_pRequestHandler->PredictContext(lParam, reinterpret_cast<LPWSTR>(channel->ReceiveBuffer()))`，返回 1 作 ack。
- `WeaselIPCServer\WeaselServerImpl.cpp:395-422` `HandlePipeMessage` 宏分发：`WEASEL_IPC_PREDICT_CONTEXT → OnPredictContext` 已注册（:417）；分发后 `resp(result)`。
- `WeaselIPC\PipeChannel.cpp:447-457` `_ProcessPipeThread`：循环 `_Receive(pipe,&msg,sizeof(msg))` → `handler(msg, [this,pipe](Msg resp){_Send(pipe,resp);})`，异常则 `_FinalizePipe`。

**假设 A（头号嫌疑）— body 在服务端 buffer 的落点偏移错位**：`_Receive` 把 ERROR_MORE_DATA 后的余量写到 `buffer.get()` 偏移 0，而 `OnPredictContext` 读 `ReceiveBuffer()`（偏移 +12）。若 body 真落在偏移 0，handler 解析的就是「错 12 字节的内容」→ ParseBody 失败 → `++parse_failures` 且不记 records——与现象吻合。**矛盾点**：生产 START_SESSION（OnStartSession 同样用 ReceiveBuffer）在线上可用，说明该机制应自洽——需要实证而不是推断。实证法：在测试 `RecordingHandler::PredictContext` 里先把收到的 buffer 前 24 个 wchar 打出来（`std::wcout << std::hex`），看 body 起始到底在偏移 0 还是 +12；或在 `OnPredictContext` 前 dump `channel->ReceiveBuffer()`。`parse_failures` 的最终值是判据：最后一次运行它若 ≥6（六次真实推送全部解析失败）即坐实「收到了但解析失败」；若 ==0 则是「根本没进 handler」。

**假设 B — handler 根本没收到（分发/线程层）**：`_ProcessPipeThread` 的 `boost::thread th([&handler, pipe, this]{...})` 每连接起新线程，若线程内 `_Receive` 抛异常（例如 body 大小/缓冲假设不符）会静默 `_FinalizePipe`。`client.UpdatePredictContext` 的返回值（ack==1？）测试没检查——先打印每次推送的返回值：ack=1 说明服务端 OnPredictContext 真的执行过（指向假设 A）；ack=0 说明没送达或 handler 空指针。

**假设 C — `AddSession` 的 EatLine 消费了不该消费的东西 / session id 不匹配**：`RecordingHandler::AddSession` 返回 1，`FindSession(ipc_id)==1 ? 1 : 0`。Echo 过了说明 channel 活着，但 StartSession 走的是带体消息（_WriteClientInfo 先 `channel <<` 三行 + `.\n`）。若 StartSession 的体处理有异常，session_id 可能不是 1 → `PredictContext(lParam≠1)` → FindSession==0 → 静默 return（不记 parse_failures！）→ records 空且 parse_failures==0。**判据同上：看 parse_failures 与 ack 返回值即可在 A/B/C 三者中二选一收敛。**

一步到位的诊断改法（推荐先做）：在测试的 `client.UpdatePredictContext` 每次调用后打印返回值；在 `RecordingHandler::PredictContext` 入口无条件打印 `ipc_id`、buffer 前 24 wchar 的 hex、并在 ParseBody 失败分支打印 buffer 全文。跑一次，三个假设当场收敛。
